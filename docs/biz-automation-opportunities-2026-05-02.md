## 3. 단계별 기회 상세

### 3.1 make_quo — 견적 작성

**확인됨 — 현재 구현 상태:**
- `OrderQuote` 모델: supplier별 unit_price, currency, lead_time_days, validity_date 필드 존재
- `CpoAgent::PriceComparisonAnalyzer`: 동일 supplier 과거 10건 평균 대비 ±15% 이상 시 경고 인사이트 자동 생성 (확인됨)
- `CpoAgent::CostSavingAnalyzer`: 유사 품목명 타 supplier 견적 중 최저가 제안 인사이트 (확인됨)
- `orders/pdf/quote.html.erb`: 견적서 PDF 뷰 존재 (확인됨)
- `RfqReplyDraftService`: RFQ 접수 확인 답변 초안 자동 생성 (Haiku, 확인됨)

**자동화 기회:**

#### A. 과거 단가 기반 견적 초안 자동 입력 (단가 추천)
- **현재 부담**: 담당자가 eCount ERP / 이메일 archive 검색 → 수동 입력. 평균 **15~20분/카드**
- **자동화 방법**: `OrderQuote` 과거 데이터 + `Product.unit_price` 자동 조회 → 견적 폼에 추천값 pre-fill
- **자동화 후**: 검토·수정 **2~3분**
- **연간 절감 시간** (추정 50건/월 × 17분 절감 × 12): **~170시간**
- **구현 난이도**: S (반나절) — DB 쿼리 + form pre-fill만
- **기술 의존**: 단순 SQL (기존 CpoAgent 로직 재활용)
- **리스크**: 단가 변동·환율 차이로 오류 입력 가능 → 반드시 사용자 검수 필요
- **ROI 점수**: ★★★★★

#### B. 공급사 자동 추천 (품목 매칭)
- **현재 부담**: 적합 공급사 탐색·연락 **20~30분/카드**
- **자동화 방법**: `Supplier`, `SupplierProduct` 모델 기반 — 품목명/category 매칭으로 최근 거래 공급사 Top 3 추천
- **자동화 후**: 목록 확인 **3분**
- **연간 절감 시간** (추정 50건/월 × 22분 절감 × 12): **~220시간**
- **구현 난이도**: S~M — supplier_products 매핑 테이블 + 추천 UI
- **기술 의존**: 단순 SQL (supplier_products 테이블 확인됨)
- **리스크**: 매핑 데이터 품질에 의존 (eCount 동기화 정확도)
- **ROI 점수**: ★★★★★

#### C. 다수 공급사 견적 요청 이메일 일괄 자동 발송
- **현재 부담**: 공급사 3~5곳에 개별 이메일 작성·발송 **30~45분/카드**
- **자동화 방법**: 추천 공급사 선택 → Gmail API로 동일 RFQ 이메일 일괄 발송 + 각 OrderQuote 레코드 생성 (rfq_reply_draft 패턴 재활용)
- **자동화 후**: 클릭 1회 + 검토 **5분**
- **연간 절감 시간** (추정 30건/월 × 35분 × 12): **~210시간**
- **구현 난이도**: M (1~2일) — Gmail send API + bulk OrderQuote 생성
- **기술 의존**: Gmail OAuth (이미 구현됨)
- **리스크**: 잘못된 RFQ 대량 발송 리스크 → 사전 미리보기 승인 단계 필수
- **ROI 점수**: ★★★★☆

### 3.2 pending_po — 고객 PO 대기

**확인됨 — 현재 구현 상태:**
- PO 관련 자동화 전무 (확인됨 — `email_sync_job.rb`는 RFQ만 인식)
- `po_no` 필드 존재 (TrackingNumber에도 PO 코드 지원, 확인됨)
- `reference_no` 추출기: `ReferenceNumberExtractor` 서비스 존재 (확인됨)

**자동화 기회:**

#### D. PO 수신 이메일 자동 인식 → 카드 자동 이동
- **현재 부담**: 이메일 수신 모니터링 → 수동 PO 번호 입력 → 단계 이동 **10~15분/카드**
- **자동화 방법**: `email_sync_job`에 PO 탐지 로직 추가 (기존 RFQ 분류기 패턴 재활용) → reference_no 매칭 → pending_po 카드에 첨부 + new_po 단계 자동 이동 제안
- **자동화 후**: 알림 확인 + 1클릭 승인 **1~2분**
- **연간 절감 시간** (추정 60건/월 × 12분 × 12): **~144시간**
- **구현 난이도**: M (1~2일) — 이메일 분류 패턴 추가 + 단계 이동 트리거
- **기술 의존**: Gmail API + LLM (PO 인식), 기존 패턴 재활용
- **리스크**: PO가 아닌 일반 메일 오인식 → 자동 이동 전 1클릭 사용자 승인 단계 필수
- **ROI 점수**: ★★★★★

#### E. PO 번호 자동 추출 + po_no 자동 입력
- **현재 부담**: PO PDF/이메일에서 번호 수동 복사 **5분/카드**
- **자동화 방법**: 첨부 PDF 텍스트 추출 (`Rfp::AttachmentExtractor` 재활용) → 정규식 + LLM으로 PO number 추출 → `po_no` 자동 입력
- **자동화 후**: 0분 (완전 자동, 검수만)
- **연간 절감 시간** (추정 60건/월 × 4분 × 12): **~48시간**
- **구현 난이도**: S (반나절) — 기존 AttachmentExtractor 재활용
- **기술 의존**: PDF 파싱 (이미 구현됨), 간단 정규식
- **리스크**: PO 번호 형식 다양 → 오추출 시 담당자 확인 Alert 필요
- **ROI 점수**: ★★★★★

### 3.3 new_po — 공급사 발주

**확인됨 — 현재 구현 상태:**
- `EcountSlipCreateJob` + `EcountApi::SlipCreateService`: new_po 단계 전환 시 eCount 매출 전표 자동 생성 (확인됨)
- `orders/pdf/purchase_order.html.erb`: 발주서 PDF 뷰 존재 — 공급사 정보, 품목, 결제 조건, 서명란 완비 (확인됨)
- 단, 발주서 이메일 발송은 수동 (확인됨 — gmail send 로직 없음)

**자동화 기회:**

#### F. 공급사에게 발주서 이메일 자동 발송
- **현재 부담**: 발주서 PDF 생성 → 이메일 작성 → 공급사 연락처 조회 → 발송 **15~20분/카드**
- **자동화 방법**: new_po 전환 시 after_update_commit에서 → PDF 생성 → Gmail API로 공급사 contact_email에 자동 발송 (EcountSlipCreateJob 패턴 참고)
- **자동화 후**: 발송 확인 **1분**
- **연간 절감 시간** (추정 60건/월 × 17분 × 12): **~204시간**
- **구현 난이도**: M (1~2일) — wkhtmltopdf PDF → Gmail attachment send
- **기술 의존**: Gmail OAuth (구현됨), wkhtmltopdf (구현됨), Supplier.contact_email 필드 (확인됨)
- **리스크**: 발주서 오발송 시 계약 분쟁 가능 → 발송 전 미리보기 + 1클릭 승인 필수 (T2)
- **ROI 점수**: ★★★★☆

#### G. eCount 발주 전표 자동 등록 (매입 전표)
- **현재 부담**: eCount ERP 수동 발주 입력 **10~15분/카드**
- **자동화 방법**: 현재 `SalesOrder` 전표만 생성됨 (확인됨). `EcountApi::SlipCreateService`에 매입 전표 (`PurchaseOrder`) 동시 생성 추가
- **자동화 후**: 0분
- **연간 절감 시간** (추정 60건/월 × 12분 × 12): **~144시간**
- **구현 난이도**: M (1일) — 기존 SlipCreateService 확장, eCount PurchaseOrder API endpoint 확인 필요
- **기술 의존**: eCount API (이미 인증 구현됨)
- **리스크**: eCount API 매입 endpoint 스펙 확인 필요 (추정 — 별도 검증 필요)
- **ROI 점수**: ★★★★☆

### 3.4 delivery_items — 납품 추적

**확인됨 — 현재 구현 상태:**
- `DueNotificationJob`: D-14, D-7, D-3, D-0 납기 알림 인앱+Google Chat (확인됨)
- `RiskAssessmentService`: 단계별 소요일 기반 납기 위험도 자동 계산 (확인됨)
- AWB/운송 추적 기능 없음 (확인됨 — tracking_codes 테이블은 RFQ/QUO/PO 번호용)

**자동화 기회:**

#### H. AWB 번호 자동 추출 + 운송사 추적 링크 자동 생성
- **현재 부담**: 공급사 발송 알림 이메일에서 AWB 번호 수동 복사 → DHL/FedEx 사이트 직접 조회 **10~15분/카드**
- **자동화 방법**: 이메일 분류기 확장 — "shipped/AWB/tracking" 패턴 감지 → AWB 번호 추출 → 운송사 판별(DHL/FedEx/대한항공) → 추적 URL 자동 생성 → 카드에 노출
- **자동화 후**: 클릭 1회로 추적 페이지 열기 **0.5분**
- **연간 절감 시간** (추정 50건/월 × 12분 × 12): **~120시간**
- **구현 난이도**: M (1~2일) — 이메일 파싱 + 정규식 AWB 추출 + tracking_codes 테이블 활용
- **기술 의존**: Gmail API (구현됨), 정규식
- **리스크**: 운송사별 AWB 형식 다양 → 매핑 테이블 사전 구축 필요
- **ROI 점수**: ★★★☆☆

#### I. 납기 지연 조기 감지 + 선제 공급사 확인 이메일
- **현재 부담**: 납기 D-day 지나서야 인지. 공급사에 능동 확인 이메일 발송 수동 **10분/건**
- **자동화 방법**: `RiskAssessmentService`가 이미 risk_level:critical/high 계산. risk_level=critical이면 공급사에게 자동 확인 이메일 초안 생성 + 1클릭 발송
- **자동화 후**: 검토·발송 **2분**
- **연간 절감 시간** (추정 20건/월 × 8분 × 12): **~32시간** (빈도 낮지만 리스크 감소 효과 높음)
- **구현 난이도**: S~M — 기존 RiskAssessmentService + RfqReplyDraftService 패턴 재활용
- **기술 의존**: LLM (Haiku), Gmail OAuth
- **리스크**: 공급사에게 불필요한 독촉 이메일 → 반드시 사용자 검토 후 발송
- **ROI 점수**: ★★★★☆ (리스크 감소 효과 포함)

#### J. 문제 유형 자동 분류 + 유사 과거 사례 추천

- **기술 의존**: LLM (Haiku), 기존 AgentInsight 인프라 (확인됨)
- **리스크**: 분류 오류 시 담당자 혼란 → 추천으로만 제공, 강제 적용 금지
- **ROI 점수**: ★★★☆☆

### 3.6 get_grn — 입고 완료

**확인됨 — 현재 구현 상태:**
- GRN 관련 자동화 전무 (확인됨)
- `get_grn` 단계 도달 시 `ecount_slip_no` 처리 없음 (확인됨)
- `orders/pdf/` 아래 GRN 전용 PDF 뷰 없음 (확인됨)
- 결제 청구서 매칭 로직 없음 (확인됨)

**자동화 기회:**

#### K. 송장/패킹리스트 OCR → GRN 자동 채움
- **현재 부담**: 수령 후 송장 내용 수동 대조·입력 **20~30분/카드**
- **자동화 방법**: get_grn 단계 첨부 PDF → `Rfp::AttachmentExtractor` 텍스트 추출 → LLM이 "수령 품목명, 수량, 단가, 송장번호" 파싱 → OrderQuote 또는 별도 GRN 필드에 자동 입력
- **자동화 후**: 검수 대조 **5분**
- **연간 절감 시간** (추정 50건/월 × 22분 × 12): **~220시간**
- **구현 난이도**: M~L (2~3일) — AttachmentExtractor(구현됨) + LLM 파싱 + GRN 전용 필드(신규 마이그레이션 필요)
- **기술 의존**: LLM (Opus 또는 Haiku), PDF 파싱 (구현됨)
- **리스크**: OCR 오류로 수량/금액 불일치 → 반드시 사용자 검수 필수, 자동 저장 금지
- **ROI 점수**: ★★★★☆

#### L. eCount 입고 전표 자동 등록
- **현재 부담**: get_grn 시 eCount 수동 입고 처리 **10~15분/카드**
- **자동화 방법**: get_grn 전환 시 after_update_commit → eCount 입고 전표 자동 생성 (GoodsReceipt API, 추정)
- **자동화 후**: 0분
- **연간 절감 시간** (추정 50건/월 × 12분 × 12): **~120시간**
- **구현 난이도**: M (1~2일) — 기존 EcountSlipCreateJob 패턴 복제, eCount GoodsReceipt API 확인 필요
- **기술 의존**: eCount API (인증 구현됨)

### 3.7 give_up — 포기

**확인됨 — 현재 구현 상태:**

- **자동화 방법**: give_up 이력 분석 → 공통 패턴 추출(발주처/품목 카테고리/계절/가격대) → 신규 RFQ 유입 시 "과거 유사 건 30%가 give_up됨" AgentInsight 생성

**자동화 기회:**

- **자동화 방법**: done 전환 시 → 담당자에게 5점 척도 평가 알림(납기준수/품질/소통) → Supplier 모델에 평점 누적 → make_quo 단계 공급사 추천 시 평점 가중치 적용

#### O. 분기 납기 준수율 리포트 자동 생성

- **구현 난이도**: M~L (2~3일) — 집계 SQL + PDF 템플릿
- **ROI 점수**: ★★☆☆☆ (시간 절감보다 의사결정 가치)

## 4. 횡단 기회 (단계 무관)

## 8. 공통 설계 원칙 (모든 자동화 공통)
