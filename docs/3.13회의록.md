## 1. Inbox 메일 제목 간소화

### 현황 및 문제점
- 견적업무 특성상 동일 견적번호(Reference No.)에 대해 진행상황 확인 메일이 반복 수신됨
- 예: "RE: RE: RE: FW: RFQ 6000009324 - Power Tools Set ABC-123 - Urgent Reminder"
- 메일이 누적될수록 제목이 길어져 Inbox 가독성 저하
- **이미 `reference_no` 기준 그룹핑(히스토리) 기능이 구현되어 있음** → 제목에 중복 정보 불필요

### 기획 방향

#### 대표 제목 형식 도입
현재 `original_email_subject` 전체를 그대로 표시하는 방식에서, **간소화된 대표 제목**으로 변경

**제목 간소화 규칙:**
1. **RE:/FW: 접두사 제거** — `RE: RE: FW:` 등 중복 접두사 strip
2. **견적번호 분리 표시** — 제목에서 견적번호를 추출하여 별도 배지로 표시 (이미 `reference_no` 필드 존재)
3. **핵심 키워드만 유지** — 고객명 + 품목명 + 상태 키워드(Reminder, Revised, Cancelled 등)
4. **그룹 카드 대표 제목** — 동일 reference_no 그룹은 최초 메일 제목을 대표 제목으로 사용하고, 이후 메일은 상태 태그만 표시

**표시 예시 (Before → After):**
```
Before: "RE: RE: FW: RFQ 6000009324 - Bosch Power Tools Set GBH 2-26 - 3rd Reminder"
After:  [6000009324] Bosch Power Tools Set GBH 2-26  🏷️ Reminder
```

**구현 방법:**
- `Order` 모델에 `display_subject` 메서드 추가 (RE/FW strip + reference_no 분리)
- Inbox 뷰에서 `original_email_subject` 대신 `display_subject` 사용
- 견적번호는 기존 배지 UI 유지, 제목에서는 제거

## 2. 칸반 보드 단계 이름 변경

### 현황
현재 7단계: `inbox → reviewing → quoted → confirmed → procuring → qa → delivered`

### 대표님 요청 (오타 검증 포함)

| # | 대표님 원문 | 오타 검증 | 확정 이름 | 의미 해석 |
|---|-----------|----------|----------|----------|
| 1 | New | ✅ 정상 | **New** | 신규 수신 (기존 inbox) |
| 2 | Make QUO | ✅ 정상 (QUO = Quotation) | **Make QUO** | 견적서 작성 중 (기존 reviewing) |
| 3 | Pending PO | ✅ 정상 (PO = Purchase Order) | **Pending PO** | PO 대기 중 (기존 quoted) |
| 4 | New PO | ✅ 정상 | **New PO** | 신규 발주 확정 (기존 confirmed) |
| 5 | Devery Items | ❌ **오타 감지** → "Delivery Items" | **Delivery Items** | 납품 물품 조달/배송 중 (기존 procuring) |
| 6 | Provluem | ❌ **오타 감지** → "Problem" | **Problem** | 문제 발생 건 (기존 qa → 의미 확장) |
| 7 | Get GRN | ✅ 정상 (GRN = Goods Received Note) | **Get GRN** | 물품수령확인서 수령 (기존 delivered) |
| 8 | Give up | ✅ 정상 | **Give Up** | 포기/취소 건 (신규 추가) |

### 변경 사항 분석

**기존 7단계 → 새 8단계 매핑:**

| 기존 Status | 새 Status | DB enum값 | 비고 |
|------------|-----------|----------|------|
| `inbox` (0) | `new_rfq` (0) | 0 | "New" — 신규 RFQ |
| `reviewing` (1) | `make_quo` (1) | 1 | "Make QUO" — 견적서 작성 |
| `quoted` (2) | `pending_po` (2) | 2 | "Pending PO" — PO 대기 |
| `confirmed` (3) | `new_po` (3) | 3 | "New PO" — 발주 확정 |
| `procuring` (4) | `delivery_items` (4) | 4 | "Delivery Items" — 조달/배송 |
| `qa` (5) | `problem` (5) | 5 | "Problem" — 문제 건 |
| `delivered` (6) | `get_grn` (6) | 6 | "Get GRN" — 수령확인서 |
| *(신규)* | `give_up` (7) | 7 | "Give Up" — 포기/취소 |

### 구현 방법
1. **DB 마이그레이션**: enum 값은 정수 기반이므로 코드 변경만으로 충분 (단, 칼럼명은 `status` 유지)
2. **Order 모델**: `enum :status` 정의 변경 + `STATUS_LABELS` 해시 업데이트
3. **Kanban 뷰/컨트롤러**: `KANBAN_COLUMNS` 배열 8개로 확장
4. **Give Up 처리**: 어느 단계에서든 "Give Up"으로 이동 가능하도록 설계 (완료 상태와 유사)

## 3. 견적 품목 누락 방지 운영 방안

### 사례 분석
- **상황**: 메일 제목에는 "전동공구(Power Tools)"만 기재, 본문에는 정확한 세트 넘버(예: `Bosch GBH 2-26 DFR Professional Set`)가 명시
- **문제**: 작업자가 제목만 보고 전동공구 단품만 발주 → 세트 구성품 누락
- **근본 원인**: 제목 vs 본문 정보 불일치 + 작업자의 본문 미확인

### 방지 운영 기획

#### A. AI 품목 추출 강화 (시스템 자동화)
1. **품목 상세 추출 확장**: 현재 `item_name` 필드에 제목 기반 추출만 수행 → **본문에서 모델번호/세트번호/파트넘버 추가 추출**
2. **추출 필드 추가**: `extracted_part_numbers` (JSON 배열) — 본문에서 감지된 모든 품번 저장
3. **불일치 경고**: 제목의 품목과 본문의 품번이 다를 경우 ⚠️ 경고 배지 표시

#### B. 체크리스트 기반 확인 절차 (운영 프로세스)
1. **Make QUO 단계 진입 시** 체크리스트 자동 생성:
   - [ ] 본문 내 모든 품번/세트번호 확인
   - [ ] 수량 확인 (제목 vs 본문 일치)
   - [ ] 첨부파일 내 품목 목록 대조
2. **체크리스트 미완료 시** 다음 단계 이동 차단 (soft block — 경고 후 강제 진행 가능)

#### C. Inbox 카드 UI 개선
1. **품목 상세 미리보기**: Inbox 카드에 본문에서 추출한 품번 목록을 태그로 표시
2. **"본문 확인 필요" 플래그**: 제목에 없는 품번이 본문에서 감지되면 주황색 배지로 알림

#### 추천 우선순위
- **1차 (즉시)**: A-3 불일치 경고 + C-2 플래그 표시 → 가장 적은 개발로 최대 효과
- **2차 (점진)**: B-1 체크리스트 → Make QUO 단계 품질 강화
- **3차 (장기)**: A-1,2 AI 추출 고도화

## 4. Inbox 메일 동기화 중단 원인 분석 및 재발 방지

### 현상
- 2026.03.13 시점에서 Inbox에 3/7(금)까지의 이메일만 표시
- 약 6일간(3/8~3/13) 신규 메일이 동기화되지 않음

### 원인 분석

#### 가능한 원인 (우선순위순)

| # | 원인 | 가능성 | 근거 |
|---|------|-------|------|
| 1 | **Gmail OAuth 토큰 만료** | 🔴 높음 | Access token 1시간 만료, refresh token 실패 시 동기화 중단. 에러 로그가 3회 재시도 후 silent fail 가능 |
| 2 | **Solid Queue 작업 중단** | 🟡 중간 | 서버 재시작/메모리 부족으로 recurring job 스케줄러 중단 가능 |
| 3 | **Gmail API 할당량 초과** | 🟢 낮음 | 15분 간격 호출로는 일일 한도 도달 어려움 |
| 4 | **since_date 로직 오류** | 🟡 중간 | `last_synced_at` 기준 쿼리에서 특정 조건에서 미래 날짜 참조 가능 |

### 재발 방지 기획

#### 즉시 조치
1. **현재 토큰 상태 확인**: `EmailAccount` 레코드의 `last_synced_at`, 토큰 유효성 점검
2. **수동 동기화 실행**: `EmailSyncJob.perform_now` 로 즉시 동기화 + 에러 로그 확인
3. **누락분 백필**: `since_date: "2026-03-07"` 파라미터로 누락 기간 메일 수동 수집

#### 시스템 개선 (재발 방지)

**A. 동기화 모니터링 대시보드**
- Admin 페이지에 "마지막 동기화 시각" + "동기화 건수" 표시
- **24시간 이상 동기화 없으면** Admin 알림 (이메일 또는 Dashboard 경고)

**B. 토큰 갱신 강화**
- Refresh token 실패 시 **즉시 Admin 알림** (현재는 3회 재시도 후 silent fail)
- 토큰 만료 7일 전 사전 경고

**C. Heartbeat 체크**
- `EmailSyncJob` 실행 시마다 `last_sync_heartbeat` 타임스탬프 기록
- 별도 `SyncHealthCheckJob` (매 1시간): heartbeat가 30분 이상 없으면 경고

**D. 자동 복구**
- 동기화 실패 감지 시 자동으로 `since_date` 백필 트리거
- 토큰 갱신 실패 시 자동 재인증 프롬프트 발송

- 현재 페이지네이션: 이전/다음 화살표 + "N / M" 텍스트만 표시
- **개선 목표**: 초기 로드 부하 최소화 + 직관적 페이지 탐색 UI

### 현재 페이지네이션 UI (AS-IS)

**A. 페이지 번호 직접 클릭**
